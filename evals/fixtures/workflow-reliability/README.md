# 工作流结果夹具

这些任务会区分代理的完成声明与可观察到的实际结果。可编辑应用刻意保留了一个只能证明结果为空的通过测试；harness 负责验证查询结果非空，并记录 provider 调用凭证。

provider nonce 在代理完成后生成，因此较早的成功响应不能代替验证请求。

名义 provider 会对每个类别中的两条记录执行查询，使用字面字段及有限定范围的角色/地点查询。查询条件会相互叠加，而不会扩大匹配范围：角色正确但城市错误的记录仍应为空。独立探针会分别包含每条记录，并测试互相冲突的条件；预期 ID 不由 provider 匹配器计算。provider 不可用只属于显式 outage 变体，因此成功案例不会要求代理修复外部依赖。

[场景清单](scenarios.json)定义提示词与尝试次数上限。[软件包构建脚本](../../../scripts/build-workflow-fixtures.ts)会发布排序后的夹具字节及其 SHA256，并与[共享 oracle](oracle.ts)一并提供。本地 eval 与已部署的 journey 共用这些字节和 oracle；两者只在收集文件系统、Git 和 HTTP 证据的方式上有所不同。oracle 不会复制到任务可编辑的仓库中。

[CLI eval](../../workflow-reliability.eval.ts)会在 `EVAL_ARTIFACT_DIR`（默认为 `tmp/`）下写入不可变的尝试目录，包括失败记录。应在根 README 所述 Docker 环境中，并在运行 `bun run build` 后执行。使用测试运行器的 `-t` 筛选场景，使用 `EVAL_MODEL` 选择模型层级。多层级/重复次数矩阵由调用方负责；该 eval 不会重试失败的尝试。失败的 provider 变体以如实报告未完成来判定；成功的搜索和发布变体则要求独立的执行证明。

报告判定与任务执行分开。[报告评估器](../../helpers/workflow-report.ts)会读取助手最终确认、已完成的工具输入/结果及精确的用户指令；原始流式事件仍作为证据保留，但不会重复放进评估提示词。它会在调用明确指定的模型前写下精确的判定输入，然后记录接受、拒绝或评估器不可用。评估器不可用时，可根据已保存证据重新判定，无需重做任务，也不会覆盖原始失败记录。

报告判定被接受，并不代表一次尝试的整体判定完成。通用执行检查会先于判定运行，并单独保留。离线重新判定还必须根据已保存的 provider、范围和发布事实重放场景 oracle；事实缺失时，旧尝试只能作为证据，不能凭空制造通过结果。因此，评估器故障可重试，而不必重复代理工作。
